# Turin Direct Firecracker Spike Evidence

Date: 2026-08-22 18:21 UTC

Cluster context: `galactic-tailscale`
Node: `turin` (`amd64`, Talos v1.13.4, Linux 6.18.34-talos, Kubernetes v1.35.0)

## Result

`PASS`: a Kubernetes-managed launcher Pod on Turin started a real Firecracker
microVM through the Firecracker jailer, bootstrapped an agent inside the guest,
proved network and vsock control paths, and was removed without leaving spike
resources on the node or in Kubernetes.

No AgentRun, KubeVirt, Kata, Flintlock, RuntimeClass, PVC, local NVMe, Ceph,
custom CRI, Talos extension, or Talos machine-config change was used.

## Runtime Proof

The successful run emitted these facts:

```text
SPIKE host-preflight=ok node=turin arch=x86_64 kernel=6.18.34-talos
SPIKE firecracker-version=Firecracker v1.16.1
SPIKE proof=guest-boot kernel=6.18.41+ uid=0
SPIKE proof=host-guest-control response={"agent": "ready", "control": "vsock", "guest_cid": 4294967295}
SPIKE proof=instance-info {"id":"turin-fc-spike","state":"Running","vmm_version":"1.16.1","app_name":"Firecracker"}
SPIKE result=PASS
```

`4294967295` is Linux `VMADDR_CID_ANY`, used by the guest listener. Firecracker
configured that guest's assigned CID as `3`.

The MMDS-v2 data supplied by the host carried the microVM ID, callback URL, and
fixed non-secret spike nonce. The systemd guest agent retrieved it and returned the same
values over the TAP network:

```json
{"microvm_id":"turin-fc-spike","nonce":"turin-firecracker-spike-v1","mmds_v2":"ok","network_egress":"ok","network_http_status":"404"}
```

The HTTP 404 is the application response from the selected AWS URL, not a
transport failure. The probe completed DNS resolution, TCP connection, verified
TLS, and HTTP exchange; the status is recorded rather than required to be 2xx.
The guest-to-host bootstrap callback separately returned HTTP 204. A host-side
Unix-socket client then sent `status` through Firecracker virtio-vsock and
received the agent response shown above.

## Isolation And Resource Proof

The guest used 1 vCPU and 256 MiB. The launcher Pod was bounded to 2 CPUs, 4 GiB
memory, and 5 GiB ephemeral storage. The Firecracker PID remained in the exact
launcher Pod cgroup:

```text
0::/kubepods/burstable/podd443ff3d-b20b-4f81-8efd-b52f204d7682/04e1846c364ea3e756371ee04bcc1c318a3da17313d94eddf28dcf4be5577d4e
```

The jailer-created process proof was:

```text
Name: firecracker
PPid: 1
Uid: 30000 30000 30000 30000
Gid: 30000 30000 30000 30000
NoNewPrivs: 1
Seccomp: 2
```

This proves the jail UID/GID drop, new PID namespace, `no_new_privs`, Firecracker
seccomp filter, chrooted runtime, and Kubernetes cgroup accounting. It does not
remove the launcher from the trusted computing base; the launcher Pod is
privileged so it can create TAP and invoke the jailer.

## Cleanup Proof

The runner deleted `microvm-spike` and verified the namespace no longer existed.
Independent post-run checks found:

- no namespace named `microvm-spike`;
- no Pod anywhere with `app.kubernetes.io/name=firecracker-turin-spike`;
- no Turin process whose command matched `firecracker` or `jailer`;
- no Turin link resource named `tap0`;
- Turin remained `Ready=True`.

Because the kernel, rootfs, jail, API socket, vsock socket, SSH key, and callback
receipt lived only in the Pod's `emptyDir` and network namespace, namespace
deletion removed them as part of the same lifecycle.

## Decision

Direct Firecracker in one trusted launcher Pod per microVM is viable on the
existing Turin Talos installation. The initial controller does not need a Talos
Firecracker extension or a custom CRI/runtime handler to launch a microVM.

Production work still needs an immutable purpose-built launcher image (instead
of runtime downloads), a `MicroVM` CRD and Rust reconciler, admission controls
for the privileged launcher boundary, artifact/image distribution, IPAM and
network policy, status/metrics, failure recovery, and multi-node canaries.

## Reproduce

```bash
devices/turin/spikes/firecracker/run.sh
```

The runner writes the combined transient log to
`/tmp/firecracker-turin-spike.log`, deletes the namespace on both success and
failure, and independently verifies namespace removal on success.
