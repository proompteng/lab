# Ofz authorization API

Ofz owns the final Tengri policy schema, action catalog, typed authorization API and durable control state.
The migration is tracked in [the implementation checklist](../../docs/tengri/ofz-implementation-status.md).
The running cluster still uses the old contract until the reviewed, coordinated hard cutover.

[`schema.zed`](schema.zed) uses immutable workspace and namespace UIDs, active platform membership, explicit workspace
roles and native expiring agent grants. Platform administration grants no workspace content access. An agent decision
must check its expiring grant and its issuer's current permission in one fully consistent bulk request.

[`authz.proto`](../../proto/proompteng/authz/v1/authz.proto) is the API authority. Rust bindings are generated by
`build.rs`. Unknown actions, mismatched resource types, name-based workspace IDs and unattested callers fail closed.
Observation and control are separate actions. HTTP application proxies and editor access are privileged even for GET.

The inventory gate accepts explicit route registrations and literal operation switches. It checks JavaScript and
TypeScript Next routes, rejects unsupported Axum composition and fallback changes, and rejects operation handling
outside the classified switch. The Codex allowlist must use its exhaustive switch with an explicit deny default.
It scans all gateway router construction and comment-normalized protobuf declarations, and checks that BFF schema
actions match its classified handlers. Computed access to the parsed discriminator requires review. Changing these
dispatch forms requires updating the inventory contract and its bypass regressions in the same review.

cd services/ofz

The policy fixture starts a disposable, loopback-only SpiceDB and an isolated PostgreSQL using the same pinned images as the cluster.
It never reads or modifies production relationships. It checks the complete human role matrix, platform membership
revocation, namespace/connector isolation, and native grant expiration. API, crash, broker and product acceptance are
separate gates; a schema fixture does not establish deployed application enforcement.

The pinned SpiceDB release retained an allowed expiration result with both dispatch caches enabled, including fully
consistent checks against PostgreSQL. The fixture disables both dispatch caches and verifies the stored expiration
before checking it. The coordinated production release must carry the same cache settings and also enforce each
grant's database-clock deadline in Ofz. Re-enabling caching requires a fresh expiration and revocation qualification.
