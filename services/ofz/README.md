# Ofz authorization API

Ofz owns platform authorization, service registration, policy onboarding and durable authorization state through
SpiceDB. [The platform package](platform/README.md) explains service/policy onboarding and relationship management;
[the architecture and cutover guide](../../docs/platform/ofz-relay.md) covers Relay and its clients.

`PlatformAuthorizationService` is the extensible platform contract. `TengriAuthorizationService` owns Tengri's existing
identity, workspace lifecycle, session and content-access operations. The former `AuthorizationService` and its
Tengri connector API are removed. Kubernetes connector execution goes through the separate Relay service.
Ofz and its existing Tengri consumers retain their coordinated image release cohort.

[`schema.zed`](schema.zed) uses immutable workspace UIDs, active platform membership, explicit workspace
roles and native expiring agent grants. Platform administration grants no workspace content access. An agent decision
must check its expiring grant and its issuer's current permission in one fully consistent bulk request.

[`authz.proto`](../../proto/proompteng/authz/v1/authz.proto) is the API authority. Rust bindings are generated by
`build.rs`. Unknown actions, mismatched resource types, name-based workspace IDs and unattested callers fail closed.
Observation and control are separate actions. HTTP application proxies and editor access are privileged even for GET.

The inventory gate accepts explicit route registrations and literal operation switches. It checks JavaScript and
TypeScript Next routes, rejects unsupported Axum composition and fallback changes, and rejects operation handling
outside the classified switch. The Codex allowlist must use its exhaustive switch with an explicit deny default.
It scans all gateway router construction and comment-normalized protobuf declarations, and checks that BFF schema
actions match its classified handlers. Computed access to the parsed discriminator requires review. Changing these
dispatch forms requires updating the inventory contract and its bypass regressions in the same review.

The policy fixture starts a disposable, loopback-only SpiceDB and an isolated PostgreSQL using the same pinned images as the cluster.
It never reads or modifies production relationships. It checks the complete human role matrix, platform membership
revocation, workspace isolation, and native grant expiration. API, crash, broker and product acceptance are
separate gates; a schema fixture does not establish deployed application enforcement.

The pinned SpiceDB release retained an allowed expiration result with both dispatch caches enabled, including fully
consistent checks against PostgreSQL. The fixture disables both dispatch caches and verifies the stored expiration
before checking it. The coordinated production release must carry the same cache settings and also enforce each
grant's database-clock deadline in Ofz. Re-enabling caching requires a fresh expiration and revocation qualification.

The Rust API uses exact SPIFFE mTLS caller identities and contract version 1. `ofz migrate` creates the checksum-bound
control schema as its separate owner; `ofz serve` verifies it and reconciles unfinished commands before listening.
The control DDL and its non-null checksum commit in one transaction. Interrupted initialization leaves neither visible;
an existing missing, null or different checksum is rejected and never filled from the current binary.
`ofz migrate-runtime` initializes or advances `tengri_control` as `tengri_migrator`. It verifies the ordered installed
SHA-256 checksums before applying any remaining packaged migrations and commits the schema and ledger in one
transaction. It serializes concurrent attempts and rejects a different owner, database, missing ledger or changed
checksum. The BFF, controller and supervisor require all seven migrations through `0007_ephemeral_oauth.sql`; they cannot
initialize their own schema. Promote Ofz and complete its migration hook before promoting those consumers.
The API reads its database password, database CA and native key from mounted files. Database TLS verifies the configured
DNS name. The API role cannot rewrite audit rows or command intent; the exporter can only read and acknowledge audit.

Concurrent access decisions share a bounded audit writer per API process. It collects at most 32 receipts for up to
five milliseconds and uses one pooled connection and durable commit for the batch. Every receipt and outbox entry
still commits before its caller receives success. Per-receipt savepoints isolate invalid sessions and SQL failures;
a failed commit acknowledges none of the batch. Policy commands retain their own atomic intent and effects transactions.
The 128-item queue bounds pending work and leaves the other SQL connections available for fresh authorization reads.
The server and initial audited transports allow thirty seconds for durable admission. Clients issue 25-second request
contexts, leaving five seconds of headroom below the server's unchanged thirty-second validation ceiling.
Ofz still rechecks current authority after committing and returns a policy decision valid for at most two seconds; receipt revalidation remains
bounded to two seconds. This processing budget does not extend the BFF's five-second signed assertion admission.
Ofz, Tengri and the BFF export traces in the background with a ten-second network budget. Diagnostic flush failures
retain their trace and event IDs for collector readback. An unsuccessful flush remains a failed verification.

Repeated controller runtime-state reads and guest health probes may reference their original durable observation
receipt. Ofz verifies its exact workload, actor, workspace, epoch, action, resource, target and recovery generation,
including the eight-hour age limit, while still re-reading current authority and policy on every call. The receipt
identifies a committed observation; it never replaces an authorization decision. Terminal cleanup cannot reuse an
observation receipt and retains a new durable audit for each submission.

Initial platform setup uses `ofz bootstrap /var/run/ofz/bootstrap/manifest.json`, followed by
`ofz activate /var/run/ofz/bootstrap/manifest.json`. Both commands require the `ofz_migrator` schema owner in
`ofz_control`. The protected manifest supplies two distinct canonical numeric GitHub IDs in `administratorGithubIds`
and distinct canonical UUIDs in `operationId` and `activationOperationId`. Use the approved, independently verified
account IDs. Keep the same manifest for every uncertain retry; usernames and email addresses are not authority.

Bootstrap requires a fresh, fenced control database. It durably records the approved intent before installing the
compiled SpiceDB schema and the two Member/Administrator assignments, plus the two exact application workload
relationships. It commits the SQL identities, immutable audit and original receipt while retaining the fence.
The existing per-member defaults remain two workspaces, one active workspace and 64 GiB, within the fleet budget.
The native schema read/write calls follow the [Authzed schema API](https://github.com/authzed/api/blob/main/authzed/api/v1/schema_service.proto).
The journal records the server's installed schema hash and rejects a changed schema during initialization or activation.

Activation requires acknowledgement of the bootstrap and all prior audit receipts, a healthy archive checkpoint,
unchanged initial administrator/workload authority and the installed schema. A fully consistent bounded read must
match exactly the six approved platform relationships; surplus principals, cross-role assignments and retired
platform objects keep activation fenced. The final authority check repeats that comparison after the audit insertion.
It rechecks archive health after its own
audit insertion before removing the platform fence. Completed retries return their original receipt and report current
fence, version, recovery generation and archive health. They cannot re-add an offboarded administrator or undo a later
recovery fence. Once both bootstrap and activation have committed, retries match the original manifest and return
the original receipts even when the binary packages a newer source schema. They do not install that schema or change
existing relationships. Unfinished initialization and activation remain bound to their original compiled schema;
installing later policy definitions requires a separate reviewed migration. Bootstrap markers use a separate namespace
from ordinary policy-command UUIDs. Audit identifies the
actual PostgreSQL owner authority rather than claiming an API SPIFFE caller.

Before running these commands in production, verify old-writer fencing, the reviewed native credential rotation and
the selected image and target. Keep the Kubernetes workspace-creation fence until the complete coordinated runtime
and identity cutover passes. Run `bash services/ofz/test-control.sh bootstrap` from the repository root for the real
CLI/PostgreSQL/SpiceDB qualification. Its explicit synthetic archive acknowledgement is only a fixture; production
requires the independent exporter and durability proof. Physical promotion fingerprints enumerate all control tables,
including the bootstrap journal, from a consistent snapshot.

Commands serialize under a dedicated PostgreSQL connection and advisory lock. Durable SQL intent precedes the atomic
native version/command-marker write; SQL effects, immutable audit, outbox and receipt commit before acknowledgement.
Retries return the original receipt without returning an agent credential again. Ownership transfer, Developer removal,
membership offboarding and grant revocation restrict SQL access in the intent transaction, so a crash after native policy
changes cannot expose an uncleansed guest. Retained homes still count against quota while quarantined.
Offboarding preserves an already approved `removing` state, including when the affected human is the owner,
a Developer or an emergency user. Only exact controller confirmation of home removal releases its quota;
offboarding cannot prevent that confirmation or release storage capacity early.
`GetCommand.workspace_removed` reports completion only for the authenticated caller's original removal command,
after that controller confirmation. The BFF waits for it before acknowledging deletion and retiring browser retry IDs.

Unbound creation reservations expire after five minutes on the database clock. Expired reservations no longer
consume quota and cannot be enrolled or reused. Their IDs remain recorded so an old retry cannot allocate new capacity.
Before claiming a slot, the controller commits `BeginWorkspaceEnrollment`, binding the reservation to the exact MicroVM
UID. This `enrolling` state remains quota-counted across the creation deadline and retries; only that UID can enroll its
home. If its owner is offboarded after that binding, enrollment records the retained home as quarantined, denies
runtime and content access, and retains its quota. The controller deletes an expired, unbound MicroVM using its exact UID and resource version before touching the
pool; its finalizer releases only a proven unclaimed candidate. Enrolled and quarantined homes remain counted until
confirmed removal.

Only the BFF submits human policy commands; the controller's separate workload branch admits its enrollment and stop
commands. Human roster and audit reads also require the exact BFF identity. Privileged policy/audit reads require
verified MFA without requiring a fresh control step-up or renewing idle activity. An approved emergency grant is projected
into the durable workspace roster with its expiry; offboarding deletes that native relationship and quarantines any
workspace exposed to emergency root access. Repeating an existing collaborator role never emits duplicate native updates. Initial authorized control
activity advances the session's idle deadline at thirty-second resolution without exceeding its absolute expiry.
Concurrent activity validates the current SQL session without rewriting a freshly extended deadline. When another
transaction holds the session row, the optional idle refresh skips that row and current session validation still runs.
Activity cannot queue an entire browser asset burst behind one durable refresh. The idle limit
can therefore expire up to thirty seconds before thirty minutes from the final control request. Observations, denied
requests and stream rechecks do not renew it. Logout binds its operation ID and original receipt to the opaque session credential and origin,
so a lost response can be retried without producing another effect or revoking another session.

The BFF supplies a fresh 256-bit credential when establishing a session and reuses the exact request for uncertain
RPC retries. Ofz binds its operation ID to the credential hash and full request fingerprint. A committed retry returns
the same still-active credential without consuming another OIDC nonce, creating a session, extending idle time, or
writing another successful establishment receipt. Changed payloads collide; expired and revoked sessions stay denied.
A live runtime epoch can only be repeated or stopped before replacement, preserving the controller's stop authority.

`AuthorizeCommand` checks human command permission before the BFF resolves an external subject. It produces an audit
receipt without changing policy, returning content or renewing idle activity. This preflight remains available during
archive loss for revocation; `ExecuteCommand` independently checks the final actor, command and current version.

Archive health requires a recent acknowledgement and no unacknowledged receipt older than sixty seconds, checked
against both the outbox and the durable sequence checkpoint. A live exporter heartbeat cannot hide a backlog. The final decision guard rechecks archive health after the native
permission response, including a failure that occurs while the request is in flight. Controller enrollment checks a
fresh state after workload authorization and cannot install new access during archive loss; stop/release remain available.

The image also packages `/bin/ofz-audit-export`, which exports bounded batches from the durable outbox to the
[Ceph recovery store](recovery.md). It requires the separate `ofz_archiver` SQL role
and verifies database TLS. Configure `OFZ_DATABASE_DSN`,
`OFZ_DATABASE_PASSWORD_FILE`, `OFZ_DATABASE_CA_FILE`, `OFZ_ARCHIVE_ACCESS_KEY_FILE` and
`OFZ_ARCHIVE_SECRET_KEY_FILE` with mounted files. The destination is the private Ceph object gateway on port 80.
This deployment uses the existing Ceph storage configuration without SSE or a separate key manager. Versioning,
COMPLIANCE retention, payload hashes, version-specific readback and archive freshness gates remain required.

The exporter holds a PostgreSQL session lease. Standbys wait for that lease; keepalives and a fifteen-second database
idle-session limit bound abandoned connections. Every batch records ordered sequences, original receipts, target
hashes and database timestamps. Its immutable key includes the complete payload hash. SQL acknowledges a batch only
after version-specific readback and COMPLIANCE retention verification. An uncertain upload reuses the stored version;
late commits below the checkpoint remain discoverable through their unacknowledged outbox entries. Empty-loop
heartbeats verify the existing independent object and bucket configuration. Storage errors never fabricate health.
Idle polls continue verifying the archive every second, but refresh its durable heartbeat only when it reaches ten
seconds old. New batches still acknowledge immediately. A verification failure immediately clears archive health;
repeated failures do not rewrite an already invalid checkpoint. The sixty-second freshness and backlog gates remain
unchanged.

The worker retries HTTP transport failures after one second while archive health remains invalid. Recovery requires
fresh bucket, retention and payload verification before another acknowledgement. Database, integrity and policy
failures still terminate the worker. `--once` reports a transport failure immediately instead of retrying.

If a lower audit sequence commits during an upload, that batch remains acknowledged while the checkpoint waits for
the lower sequence. The next poll exports the missing receipt before advancing the checkpoint. This normal commit
race does not invalidate archive health or terminate the exporter. Missing outbox entries, failed uploads, invalid
retention, and actual acknowledgement changes still fence access.

Run `bash services/ofz/test-control.sh archive` for the real owner CLI, PostgreSQL and S3 qualification. It uses the
production credential generator, writer policy and synchronized SQLite/object configuration. It proves initial
archive-gated activation, deletion/retention denial, uncertain uploads, out-of-order commits, archive loss and

Kubernetes exporter adoption, independent database/home backups or a completed restore.

Controller runtime reads repeat native workload authorization after the audit, then compare workspace authority and
global policy/fence state from one SQL snapshot before disclosure. Their final two-second window starts before the
native recheck, and the response identifies the revision in its durable access receipt. Restrictive intent can quarantine
a workspace before native policy finalization advances the global version; an in-flight read must abort if that workspace
authority changes, even when the policy version stays the same.

Initial audited calls may wait up to five seconds for durable commit. Ofz rechecks authority after that commit before
issuing a decision valid for at most two seconds on both the API and database clocks, still capped by the request
deadline and session or grant expiry. A clock difference that leaves no valid window fails closed.
Only the audit transaction receives a five-second SQL statement timeout; ordinary connections retain their two-second
statement and one-second lock limits after it commits.
Receipt renewals keep their two-second request budget and recheck current authority. A compound guest operation
authorizes its child, refreshes the parent through its original receipt, then intersects both decision deadlines.
Redeemed terminal and preview capabilities regenerate that same request budget. Preview redemption starts the budget
after its transaction commits; capability expiry and session/runtime bindings remain unchanged.
Access responses and renewals keep their receipt's audited native revision while rechecking current permission, scope,
policy version and recovery state. Advancing native read tokens alone do not invalidate unchanged authority. Receipts
without a recorded native revision cannot renew; callers must open a fresh audited access.

The Landing BFF now uses a schema-generated Ofz client with exact SPIFFE peer verification. Its dedicated Keycloak
realm requires GitHub brokerage and verified passkeys. Ofz verifies issuer, audience, nonce, immutable numeric GitHub
identity, authentication time and assurance level before issuing a hash-only opaque SQL session. Reauthentication
revokes the previous browser credential in the same transaction. Failed establishment records an immutable denial
without storing the ID token. Platform membership remains necessary after successful identity-provider authentication.

A workspace Viewer has metadata access by default. Content requires an explicit Owner-approved observation scope
stored with the collaborator: selected file roots, conversation IDs, terminal IDs, screenshot permission and response
budgets. Scope changes use the same versioned, audited command as role assignment. A same-role change updates the
scope; removing it immediately makes subsequent content checks fail, including checks for an existing stream receipt.
Owners and Developers retain their existing privileged authority. Viewer scopes cannot grant execution, lifecycle,
editor or application-preview access. The roster returns the exact stored scope. File roots and selected IDs reject
control characters, traversal and known credential paths where applicable. Scoped guest content stays denied until
the separate bounded observer handlers are implemented and qualified.

The BFF limits complete encoded commands to 64 KiB, including JSON escaping and metadata. Its gRPC sender and the API
accept protobuf envelopes up to 128 KiB so an accepted command still fits after the BFF adds its authenticated context,
resolved identity and request hash. The public-body and private-envelope limits remain enforced independently.

A native Viewer relationship cannot authorize content without its committed SQL role and scope. Changing a Viewer
scope clears content access in the durable intent transaction, before native finalization advances the policy version.
The final decision reads scope, session, runtime and platform authority from one SQL snapshot after its audit write or
stream-receipt lookup; changed authority returns a denial and records it. The real control fixture reproduces both
pending-grant and in-flight narrowing failures before their fixes and passes with 55 commands and 186 immutable
receipts afterward. The audit-timing cases also verify that a slow commit cannot return an expired permit or extend
the original request deadline.

The Access UI submits typed, versioned commands through the BFF. It verifies GitHub usernames against numeric IDs,
requires fresh MFA for changes, shows quota usage and audit receipts, and retries an uncertain command with its original
operation ID. The independent `/access` page permits policy administration without starting a guest or opening content.
Before preparing a command again, the BFF checks for its committed receipt under the active platform session. Ofz
matches the hash of the original validated request, so transfers and self-demotions can recover a lost reply after
the caller loses the original permission without resolving a GitHub username again. A changed payload with the same
operation ID is rejected. Cancelled or rejected OIDC callbacks clear the OAuth binding cookie and return the controlled
authentication failure without requiring an authorization code.

## API image delivery

`nix build .#ofz-image` builds the API for the native Linux architecture from the locked Cargo dependencies, canonical
authorization protobuf, policy catalog, and all three database migrations. The runtime contains the API and certificate
roots, runs as UID/GID 65532, and exposes the mTLS API on port 9443. The same binary provides `serve`, `migrate`,
`migrate-runtime`, `bootstrap` and `activate`.

The Ofz workflow first qualifies policy, durable control state, synchronous physical promotion, and real browser
identity. Its existing Nix image workflow then checks both native architectures. A successful main build publishes the
multi-architecture index, release receipt, and immutable run-qualified Kargo alias. Pull requests build without
publishing. Warehouse/Stage enrollment and API activation remain separate reviewed desired-state changes; creating an
image does not admit users or activate runtime clients.

Ofz image-packaging and documentation changes do not rebuild native Tengri guests. Ofz implementation, Cargo dependencies,
build script, migrations, policy schema, operation catalog, authorization protobuf, and KVM launcher changes retain the
shared runtime and native KVM qualification. The paired guest build uses its existing registry cache when its inputs are unchanged.

Production error reporting and trace propagation use the existing GlitchTip and Tempo services. RPC traces retain the
numeric status code. Expected session expiry, denied requests and client validation failures remain traceable without
creating server-error issues; transport, deadline, capacity and internal failures still emit GlitchTip events with a
bounded `grpc_code` tag and a status-specific title. See
[Tengri observability](../tengri/README.md#error-reporting-and-request-traces) for the privacy, network and rollout
contract. `ofz telemetry-check` emits a synthetic error and trace using the deployed configuration without opening a
database connection or changing authorization state. Confirm the returned IDs in both collectors.
