# Apps and services deprecation matrix

The tracked tree has **18 apps and 36 services**. The matrix includes the removed directory so the decision is
reviewable against the audit base.

## How to read the matrix

- `ACTIVE_PROD`: the directory supplies an enabled GitOps workload, image, or generated runtime artifact. This includes
  deployed infrastructure and canaries, not just user-facing products.
- `ACTIVE_TOOLING`: retained for a local, CI, developer, or operator workflow without an enabled deployment of this source.
- `DISABLED_ARCHIVED`: disabled deployment or legacy source retained for a documented dependency or recovery path. Build,
  test, and workspace references may still exist.
- `DEAD_ORPHAN`: no repository deployment, image consumer, build or CI input, workspace membership, or inbound code or test
  reference. Only this class is eligible for deletion.

GitOps names and enablement come from the [product](../../argocd/applicationsets/product.yaml) and
[platform](../../argocd/applicationsets/platform.yaml) ApplicationSets and their rendered inputs under
[`argocd/applications/`](../../argocd/applications/). The other root ApplicationSets and direct Applications were
checked as well. “Off” means `enabled: "false"` in desired state; this is a repository audit, not a live cluster readback.

Nix entries are relative to [`nix/images/`](../../nix/images/) unless noted; their consumers were checked in
[`flake.nix`](../../flake.nix). Workflow filenames are relative to [`.github/workflows/`](../../.github/workflows/);
the [impact map](../../.github/ci/impact-map.yml), [root-script map](../../.github/ci/root-script-map.yml), and
reusable jobs were checked for indirect inputs. Workspace membership means an actual manifest selected by
[`package.json`](../../package.json) and present in [`bun.lock`](../../bun.lock), or a module in
[`go.work`](../../go.work), not just a directory matching a glob. A dash means no component-specific entry was found in
that column. Evidence is representative for retained rows; a single consumer is enough to rule out deletion.

Inbound checks searched tracked files outside each directory for paths, package and module names, image names, and
runtime aliases, then distinguished actual imports, build inputs, and test bindings from same-name matches.

## Deletion evidence

Only `apps/baozi` crossed the deletion gate. It was a standalone Bun Source-to-Image builder, with a local
`Makefile`, `test/run`, and example app under `test/test-app/`. Those files exercised the builder from inside the
same tree; no outside test or workflow invokes them. It had no `package.json` or other workspace manifest. The Bun
workspace glob and repository-wide lint do not require this directory to exist.

The pre-deletion search can be repeated with Git (the content and filename probes below should print no matches):

```sh
base=2a59bec11d3ffe4f9987183440992ac4daa7b67f
git ls-tree -d --name-only "$base:apps"
git ls-tree -d --name-only "$base:services"
git grep -liI -F baozi "$base" -- . ':(exclude)apps/baozi/**'
git ls-tree -r --name-only "$base" | grep -v '^apps/baozi/' | grep -i baozi
```

The name probe includes the builder and its registry image suffix. Shared S2I terms also match the separate
`apps/base` builder and other function scaffolds; they are not references to Baozi. Unlike Baozi, `apps/base`
has a concrete consumer: `apps/nata/func.yaml` identifies its image as the function's S2I builder. No service
directory cleared the same deletion gate.
